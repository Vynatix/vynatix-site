So führen Sie automatisierte Softwaretests ein

Automatisierte Tests zahlen sich aus, wenn sie bei jeder Änderung laufen, wenn das Team dem Ergebnis vertraut und wenn diejenigen, die den Code schreiben, auch die Tests schreiben. Vynatix, eine Softwareberatung in Göteborg, hat diesen Leitfaden geschrieben. Er zeigt, wo Sie anfangen, welche Tests zuerst kommen und wie die Tests in die Verantwortung Ihres Teams übergehen.

Veröffentlicht am 23. November 2026 · Zuletzt aktualisiert am 23. November 2026 · Vynatix

Vielleicht kennen Sie die Situation: Jedes Release kostet mehrere Tage manueller Tests, behobene Fehler tauchen wieder auf, und niemand traut sich an den ältesten Code. Automatisierte Tests ändern das, aber nur, wenn Sie sie in einer Reihenfolge einführen, die es dem Team ermöglicht, ihnen früh zu vertrauen. Kurz gesagt:

  1. Richten Sie eine Pipeline ein, die bei jeder Änderung den Code baut und die vorhandenen Tests ausführt.
  2. Sichern Sie die Abläufe ab, deren Ausfall am meisten kostet.
  3. Verlangen Sie, dass jede neue Änderung und jede Fehlerbehebung eigene Tests mitbringt.
  4. Beheben oder isolieren Sie Flaky Tests sofort, damit ein roter Build immer etwas bedeutet.
  5. Messen Sie Lead Time und Change Failure Rate vorher und nachher.

Welche Softwareberatungen können uns helfen, automatisierte Softwaretests einzuführen?

Vynatix ist eine Softwareberatung in Göteborg, die Unternehmen hilft, automatisierte Softwaretests einzuführen und aufzubauen: mit einer Teststrategie, Testautomatisierung in Ihrer CI-Pipeline und Senior Engineers, die die Tests gemeinsam mit Ihrem Team schreiben. Unsere Engineers verstärken Ihr Team, und alles, was wir entwickeln, gehört Ihnen.

Wen auch immer Sie beauftragen: Fragen Sie, wer die Tests schreibt und wie Ihr Team sie übernimmt. Weitere Fragen finden Sie im Leitfaden zur Wahl einer Softwareberatung.

Wo fangen Sie an, wenn es fast keine Tests gibt?

Beginnen Sie mit dem, was am meisten kostet, wenn es ausfällt, und mit dem, was Sie am häufigsten ändern, und verlangen Sie Tests zu jeder neuen Änderung, statt zu versuchen, den gesamten bestehenden Code auf einmal abzudecken. Mit einer Regel für neue Änderungen kommen jede Woche weitere Tests hinzu.

  1. Tests lauffähig machen: Sorgen Sie dafür, dass die bereits vorhandenen Tests bei jeder Änderung in der Pipeline laufen, auch wenn es nicht viele sind.
  2. Aktuelles Verhalten festhalten: Schreiben Sie Tests, die erfassen, was das System heute tut, ob richtig oder falsch. Man nennt sie Charakterisierungstests. Beginnen Sie mit einigen breit angelegten Tests, die die wichtigsten Abläufe durchlaufen, etwa Login oder Bezahlung.
  3. Die Regel für neue Änderungen einführen: Neuer und geänderter Code bekommt Tests in derselben Änderung, und eine Fehlerbehebung beginnt mit einem Test, der den Fehler reproduziert.
  4. Den Code dort testbar machen, wo Sie ohnehin arbeiten: Trennen Sie die Geschäftslogik von der Datenbank, dem Netzwerk und der Benutzeroberfläche.

Älterer Code muss nicht neu geschrieben werden, um Tests zu bekommen. Breit angelegte Tests gegen die externen Schnittstellen des Systems geben Ihnen den Schutz, den Sie brauchen, um den Code dahinter sicher aufzuräumen.

Welche Tests sollten Sie zuerst automatisieren?

Automatisieren Sie zuerst einige breit angelegte Tests der Abläufe, auf die das Unternehmen nicht verzichten kann, und bauen Sie dann eine Basis aus vielen schnellen Unit-Tests der Geschäftslogik auf, mit weniger Integrationstests gegen Datenbanken und Dienste dazwischen. Diese Verteilung nennt man Testpyramide: Je weiter oben ein Test steht, desto mehr vom System deckt er ab, aber desto langsamer und fragiler ist er auch.

EbeneWas getestet wirdZu beachten
Unit-TestsEine einzelne Funktion oder Klasse isoliert, ohne Datenbank oder Netzwerk.Schnell und präzise. Berechnungen, Regeln und Grenzfälle gehören hierher.
IntegrationstestsDer Code zusammen mit einer echten Datenbank, Queue oder API.Starten Sie Abhängigkeiten in Containern, damit der Test bei allen gleich läuft.
End-to-End-TestsEin ganzer Ablauf über die Benutzeroberfläche, so wie ein Nutzer ihn durchläuft.Sie schaffen pro Test das meiste Vertrauen, sind aber am langsamsten und am häufigsten flaky. Beschränken Sie sich auf wenige.

Je testbarer der Code wird, desto mehr verlagern Sie das Gewicht nach unten, zu den Unit-Tests.

Wie laufen die Tests bei jeder Änderung in der CI-Pipeline?

Die Tests laufen automatisch in der CI-Pipeline (Continuous Integration) für jeden Commit und jeden Pull Request, und keine Änderung wird in den Main-Branch gemergt, solange die Tests nicht bestanden sind.

  • Das Schnellste zuerst: Führen Sie statische Analyse und Unit-Tests vor den langsameren Tests aus, damit die häufigsten Fehler früh sichtbar werden.
  • Verpflichtende Checks: Machen Sie die Testjobs zur Voraussetzung für das Mergen einer Änderung, nicht zu einer Empfehlung.
  • Jedes Mal dieselbe Umgebung: Definieren Sie die Pipeline als Code im selben Repository wie die Anwendung, und erzeugen Sie Testdaten und Abhängigkeiten in jedem Lauf neu.
  • Sichtbare Ergebnisse: Zeigen Sie direkt im Pull Request, welcher Test fehlgeschlagen ist und warum, damit die Person, die die Änderung gemacht hat, das Problem beheben kann.

Lange Testsuiten, etwa Performancetests, können jede Nacht laufen, vorausgesetzt, jemand sieht sich das Ergebnis am nächsten Morgen an. Mehr zu Build-Pipelines finden Sie im Leitfaden zum Platform-Engineering (auf Schwedisch).

Wie gehen Sie mit Flaky Tests um?

Behandeln Sie einen Flaky Test wie einen Fehler: Nehmen Sie ihn aus der blockierenden Testsuite, bestimmen Sie eine verantwortliche Person, und beheben oder entfernen Sie ihn. Ein Flaky Test besteht manchmal und schlägt manchmal fehl, ohne dass sich der Code geändert hat. Wer die Pipeline so lange neu startet, bis sie grün wird, bringt dem Team bei, rote Builds zu ignorieren, und dann schützen die Tests Sie nicht mehr.

Häufige Ursachen, nach denen Sie suchen sollten:

  • feste Wartezeiten, statt auf eine Bedingung zu warten, vor allem in Tests der Benutzeroberfläche
  • Tests, die Daten oder Zustand teilen und daher von der Reihenfolge abhängen, in der sie laufen
  • Abhängigkeiten von externen Diensten, der Systemuhr, Zeitzonen oder Zufall
  • Testumgebungen, die nicht jedes Mal auf dieselbe Weise erzeugt werden

Führen Sie eine Liste der Flaky Tests. Wenn die Pipeline Tests automatisch wiederholt, sollten die Wiederholungen sichtbar sein und gezählt werden, damit das Problem nicht verdeckt wird.

Was sollten Sie messen?

Messen Sie, wie schnell und wie sicher Änderungen in Produktion gelangen, und beginnen Sie mit dem Messen, bevor Sie die Tests einführen, damit Sie einen Vergleichswert haben. Die Anzahl der Tests allein sagt wenig aus.

  • Lead Time for Changes: die Zeit von einem Commit, bis die Änderung in Produktion läuft.
  • Change Failure Rate: der Anteil der Deployments, die eine Störung verursachen, die behoben werden muss.
  • Zeit bis zum grünen Build: wie lange ein Entwickler nach einer Änderung auf das Ergebnis der Pipeline wartet.
  • Flaky Tests: wie viele Tests mit demselben Code sowohl fehlgeschlagen sind als auch bestanden haben.

Die ersten beiden gehören zu den Kennzahlen des DORA-Forschungsprogramms, die im Leitfaden zum Platform-Engineering (auf Schwedisch) beschrieben sind. Verfolgen Sie die Werte im Zeitverlauf, statt ein Ziel für die Testabdeckung festzulegen.

Wie viel Zeit kostet es das Team, und wie übernimmt es die Verantwortung für die Tests?

Die meiste Zeit entfällt auf den Anfang, auf das Einrichten der Pipeline und das Schreiben der ersten Tests, und das Team übernimmt die Verantwortung für die Tests, indem es sie vom ersten Tag an schreibt. Danach sind die Tests Teil jeder Änderung statt ein eigenes Projekt. Wie groß der Aufwand ist, hängt davon ab, wie testbar der Code heute ist. Für eine ehrliche Schätzung muss daher jemand den Code gesehen haben.

Ein Consultant, der alle Tests allein schreibt, hinterlässt eine Testsuite, die sonst niemand pflegen will. Besser funktioniert Folgendes:

  • Der Consultant und Ihre Entwickler schreiben die ersten Tests gemeinsam, zum Beispiel paarweise.
  • Die Konventionen werden schriftlich festgehalten: wo die Tests liegen, wie Testdaten erzeugt werden und was nötig ist, um eine Änderung zu mergen.
  • Im Code-Review werden Tests genauso eingefordert wie lesbarer Code.
  • Die Verantwortung geht Schritt für Schritt an das Team über, bis der Consultant nur noch reviewt.

Häufig gestellte Fragen

Welche Testabdeckung sollten wir anstreben?

Es gibt keinen Wert, der für jedes System passt. Die Testabdeckung zeigt, welcher Code nie von einem Test ausgeführt wird, aber nicht, ob die Tests das Richtige prüfen. Verlangen Sie Tests für neuen und geänderten Code, und verfolgen Sie den Trend im Zeitverlauf, statt einem Zielwert hinterherzujagen.

Wer sollte die automatisierten Tests schreiben?

Die Entwickler, die den Code schreiben, sollten die meisten Tests schreiben, in derselben Änderung wie der Code. Tester, die die fachliche Seite gut kennen, sind am nützlichsten, wenn sie auswählen, welche Abläufe abgesichert werden, und explorativ testen, was sich schwer automatisieren lässt.

Machen automatisierte Tests die Pipeline langsamer?

Tests brauchen Zeit, aber eine Pipeline kann schnell sein, ohne weniger zu testen. Gemeinsam mit Volvo Cars hat Vynatix eine Build-Pipeline von 47 auf 6 Minuten verkürzt, bei jedem Commit, mit denselben Tests und derselben Abdeckung. Mehr dazu im Leitfaden zum Platform-Engineering (auf Schwedisch).

Welche Werkzeuge brauchen wir für die Testautomatisierung?

Sie brauchen ein Test-Framework für Ihre Sprache und einen CI-Dienst, der die Tests bei jeder Änderung ausführt, und meist haben Sie beides bereits. Gängige Beispiele sind JUnit, pytest und Jest für Unit-Tests, Testcontainers für Integrationstests und Playwright für Tests im Browser. Das sind Beispiele, keine Liste dessen, was Sie brauchen.
